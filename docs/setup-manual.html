開始之前

這套系統由三個免費服務組合而成，各自負責一件事。你要做的，就是分別去申請，把它們給你的「一長串英文數字」貼到 GitHub，最後按一個按鈕。

服務負責什麼免費額度
Neon存放所有預約與成員資料永久免費，資料不會過期
Brevo寄出驗證信、通知信、提醒信每天 300 封
Render實際執行網站，並提供免費網址永久免費，閒置會休眠
GitHub存放程式、按鈕部署、定時寄提醒信公開儲存庫免費

先準備一個記事本

接下來會請你複製好幾組很長的英文數字。建議先開一個記事本暫時貼著，最後一次貼到 GitHub。全部設定完成後，請把記事本刪掉。

整體流程圖

先看懂這張圖，後面每一步都只是在填其中一格。

0建立 GitHub 儲存庫

程式要先放上 GitHub，後面的「按鈕部署」才有東西可以部署。這是全程唯一需要打指令的一步，之後所有操作都在網頁上完成。

⚠ 請選 Public（公開），這關係到費用

提醒信排程每 15 分鐘執行一次，一個月約 2,880 次。GitHub 的計費方式是每次執行不到一分鐘也算一分鐘：

Public 公開：Actions 執行時間無限、免費 ✅
Private 私有：免費帳號每月只有 2,000 分鐘 → 會超額，就不再是 NT$0 ❌

你的密碼與金鑰不會外洩——它們存放在 GitHub Secrets 裡是加密的，公開儲存庫的訪客看不到，執行紀錄中也會自動遮蔽成 ***。公開的只有程式碼本身。

先認識這三個分頁

之後所有操作都圍繞著儲存庫上方的三個分頁，先記住哪件事在哪裡：

建立空的儲存庫

  1. 登入 github.com。
  2. 點右上角的 +（加號，在頭像左邊）→ New repository。
  3. Repository name 輸入 booking-system。
  4. Description 留空即可。
  5. 選 Public（原因見上方警告）。
  6. 下面三個選項全部不要勾：Add a README file、Add .gitignore、Choose a license。
  7. 點綠色的 Create repository。
  8. 下一頁會出現一段指令，先不要照它做，只記下最上面那串網址：https://github.com/你的帳號/booking-system.git

⚠ 第 6 步是最常見的卡關點

只要勾了其中任何一個，GitHub 會先幫你建立一個檔案，接下來上傳程式時就會因為「兩邊內容對不起來」而被拒絕。真的勾到了也不難處理，把儲存庫刪掉重建一個就好。

把程式上傳上去

在你電腦上的專案資料夾執行以下兩行（把網址換成你剛剛記下的那一串）。在 Claude Code 裡可以直接在輸入框用 ! 開頭執行：

git remote add origin https://github.com/你的帳號/booking-system.git git push -u origin main

第一次推送時，Windows 會跳出瀏覽器要你登入 GitHub 授權，照著點完即可。完成後回到 GitHub 重新整理，就會看到 app、tests、docs、SETUP.md 等檔案。

✓ 這一步只需要做一次

程式上傳之後，日後的部署、改設定、退版全部都在網頁上點按完成，不需要再打任何指令。

1建立資料庫（Neon）

資料庫是存放所有預約紀錄的地方。Neon 的免費方案資料不會過期，這也是我們沒有選其他家的原因。

  1. 打開 neon.com，按右上角的 Sign up。
  2. 選擇 Continue with GitHub，用你的 GitHub 帳號登入。
  3. 建立專案：名稱輸入 booking，其他保持預設，按 Create project。
  4. 畫面上會出現一段以 postgresql:// 開頭的長字串，標示為 Connection string。
  5. 按複製，貼到記事本，註明這是 DATABASE_URL。

它長這樣

postgresql://neondb_owner:········@ep-xxxx.ap-southeast-1.aws.neon.tech/neondb?sslmode=require

2設定寄信服務（Brevo）

系統需要寄出驗證信、預約確認信與會議提醒信。免費方案每天 300 封，對 200 人的組織綽綽有餘。

先確認寄件人地址

  1. 到 brevo.com 按 Sign up free 註冊，並到信箱點擊驗證連結。
  2. 左側選單找到 Senders, Domains & Dedicated IPs。
  3. 按 Add a sender，填入寄件名稱與電子郵件地址（例如公司行政信箱）。
  4. Brevo 會寄確認信到那個地址，點擊裡面的連結完成確認。
  5. 把這個地址記到記事本，註明 EMAIL_FROM_ADDRESS。

再取得 API 金鑰

  1. 點右上角頭像 → SMTP & API，切換到 API Keys 分頁。
  2. 按 Generate a new API key，名稱輸入 booking。
  3. 畫面顯示一串以 xkeysib- 開頭的文字。
  4. 立刻複製貼到記事本，註明 EMAIL_PROVIDER_API_KEY。

⚠ 這串金鑰只會出現一次

關掉視窗就再也看不到了。如果不小心關掉，重新產生一組新的即可，舊的可以直接刪除。

3建立網站主機（Render）

Render 負責實際執行系統，並提供一個 .onrender.com 的免費網址。

  1. 到 render.com 按 Get Started，用 GitHub 帳號登入。
  2. 按 New + → Web Service，選擇這個系統所在的儲存庫。
  3. 填寫設定：
    • Name：例如 meeting-room-booking（會變成你的網址）
    • Language：Python 3
    • Build Command：pip install -r requirements.txt
    • Start Command：gunicorn "app.web.app:build_wsgi_app()" --bind 0.0.0.0:$PORT
    • Instance Type：Free
  4. 把 Auto-Deploy 設為 No。我們要用 GitHub 的按鈕部署，而不是每次改動就自動部署。
  5. 按 Create Web Service。第一次會啟動失敗，這是正常的，因為環境變數還沒設定。
  6. 複製頁面最上方的網址（例如 https://meeting-room-booking.onrender.com），註明 APP_BASE_URL。
  7. 左側 Settings → 往下找到 Deploy Hook，複製那串網址，註明 RENDER_DEPLOY_HOOK_URL。

環境變數稍後再回來填

下一步整理好九項設定後，請回到 Render 左側的 Environment，把其中的前八項加進去（不含 Deploy Hook，那個只有 GitHub 需要）。

4貼上九項設定

現在把記事本裡的東西貼進 GitHub。名稱必須一字不差，包含大小寫與底線。

名稱內容來源
DATABASE_URL資料庫連線字串步驟 1
EMAIL_PROVIDER_API_KEY寄信服務 API 金鑰步驟 2
EMAIL_FROM_ADDRESS系統寄信的寄件人信箱步驟 2
APP_BASE_URL你的網站網址步驟 3
SESSION_SECRET保護登入狀態的隨機字串自己產生
ADMIN_EMAIL你（管理員）的電子郵件自己決定
ADMIN_INITIAL_PASSWORD管理員第一次登入的密碼自己決定
CRON_SECRET保護提醒信排程的隨機字串自己產生
RENDER_DEPLOY_HOOK_URLRender 部署金鑰網址步驟 3

兩個「隨機字串」怎麼生？

只要夠長又難猜就好，你不需要記住它們。隨手在鍵盤上打 40 個以上的英數字即可，例如 k8Fq2mZp7Lw4Rt9YvXb3Nc6Hd1Js5Gk0Aq2Wf8E。兩個請使用不一樣的內容。

貼上的位置

  1. 在 GitHub 打開儲存庫，點上方 Settings。
  2. 左側 Secrets and variables → Actions。
  3. 按 New repository secret，填入名稱與內容，按 Add secret。
  4. 重複直到九項全部加完。
  5. 回到 Render 的 Environment，把前八項再貼一次，按 Save Changes。

✓ 打錯了也不要緊

部署時系統會逐一檢查，缺少或名稱打錯的項目會被直接列出名稱，回來補上再按一次即可。不會有「不知道哪裡錯了」的情況。

5按下部署按鈕

這是唯一一個「執行」的動作：Actions 分頁 → Deploy → Run workflow。

先啟用 Actions

  1. 在儲存庫點上方 Actions。
  2. 若出現藍色提示「Workflows aren't being run on this repository」， 點 I understand my workflows, go ahead and enable them。
  3. 左側應該會列出三項：CI、Deploy、Reset。（提醒信的排程不在 GitHub，見步驟七。）

執行部署

  1. 左側清單點 Deploy。
  2. 右側灰色提示條的右邊有 Run workflow 按鈕，點它。
  3. 跳出的小面板中，Use workflow from 保持 Branch: main，再點綠色的 Run workflow。
  4. 幾秒後重新整理頁面，會看到一列黃色圓點代表執行中；點進去可看即時進度。
  5. 等待 3 到 8 分鐘。
  6. 看到綠色勾勾後往下捲，「部署結果」裡就有你的網站網址。

如果是紅色叉叉

點進該次執行，左側找到紅色的步驟點開，往下捲到紅色文字，對照下表：

畫面上的訊息怎麼處理
ERROR: missing required secret(s): 後面列出名稱 回到步驟 4 把那幾項補上，注意大小寫要一模一樣
缺少 Secret：RENDER_DEPLOY_HOOK_URL 回 Render → Settings → Deploy Hook 複製網址後補上
「執行測試」步驟失敗 是程式本身的問題，把訊息保留下來尋求協助
「部署後健康檢查」失敗 先直接開網站看看能不能開。常常只是主機還在喚醒，等一分鐘後重跑一次部署即可

✓ 重複部署是安全的

修正後再按一次 Run workflow 即可。系統不會重複建立管理員帳號或範例會議室，也不會弄亂既有資料。

6第一次登入

  1. 打開你的網站網址。第一次可能要等將近 1 分鐘，這是免費方案的喚醒時間。
  2. 用 ADMIN_EMAIL 與 ADMIN_INITIAL_PASSWORD 登入。
  3. 系統會立刻要求你設定新密碼，請設定一組只有你知道的。

⚠ 為什麼一定要改密碼

初始密碼是明文存在 GitHub 的設定裡，任何能看到儲存庫設定的人都可能知道它。因此系統強制你在第一次登入時更換，不改就不能使用任何功能。

接著建議做這三件事

  • 會議室：系統預先建立了三間範例，請改成你們實際的會議室。
  • 系統設定：確認預約規則（每次最長時數、可預約多久以後、每人可保留幾筆）符合需求。
  • 邀請成員：用邀請功能寄出連結，收到的人填完資料就能直接使用，不需要再審核。

7開啟自動提醒信

系統會在會議開始前寄提醒信。網站自己不會計時，要有人從外面定時敲門，這件事交給免費的 cron-job.org。

7-1　註冊 cron-job.org

  1. 打開 console.cron-job.org，點 Signup 用電子郵件註冊，收信點驗證連結。
  2. 登入後會看到一個空的工作列表（Cronjobs）。完全免費，不需要信用卡。

7-2　建立「保持喚醒」工作

  1. 點右上角 CREATE CRONJOB。
  2. Title：填 Keep awake
  3. URL：填你的網址加上 /api/health，例如 https://你的網站.onrender.com/api/health
  4. Execution schedule：選 Every 10 minutes。沒有這個選項就選 Custom，minutes 勾 0、10、20、30、40、50。
  5. 其他都不用動，點 CREATE。

7-3　建立「提醒信」工作

  1. 再點一次 CREATE CRONJOB。
  2. Title：填 Reminders
  3. URL：填你的網址加上 /api/cron/send-reminders
  4. Execution schedule：選 Every 15 minutes。
  5. 展開下方的 ADVANCED。
  6. Request method：從 GET 改成 POST。這一項改錯會一直失敗。
  7. 找到 Headers，點 ＋ 新增一列：
    名稱填 X-Cron-Secret，值填你在步驟四設定的 CRON_SECRET 那一串字（大小寫要完全一樣）。
  8. 點 CREATE。

7-4　立刻測一次

  1. 點列表裡的 Reminders，再點 TEST RUN。
  2. 看結果的 Status：200 就是成功。
看到的狀態代表什麼怎麼修
200成功設定完成，不用再做什麼
401 / 403X-Cron-Secret 不對回 7-3 重新貼一次那串字
404網址打錯檢查有沒有少打 /api/cron/send-reminders
405忘了改成 POST回 7-3 的 ADVANCED 把 Request method 改成 POST
Timeout主機還在睡先去 Keep awake 按一次 TEST RUN，等一分鐘再回來測

⚠ 定期看一眼管理後台首頁

上面會寫「提醒信工作最後執行時間」。如果那個時間停在很久以前，登入 cron-job.org → 點那個工作 → 把 Enabled 打開 → 按 TEST RUN 確認變成 200。順便看一下 Keep awake 是不是也停了，那通常才是真正的原因。

關於免費主機的用量

「保持喚醒」會讓系統整天不休眠。Render 免費方案每月有 750 小時，一個月約 730～744 小時，所以單獨這一個網站是夠的。但如果同一個 Render 帳號下再開第二個服務就會超過額度——到時候把「保持喚醒」改成每 14 分鐘一次，或改用付費方案。

日後的操作

系統上線之後，大部分事情不需要碰 GitHub。先看看哪些事該去哪裡做。

管理後台改預約規則、新增會議室、邀請成員、審核註冊、調整等級——全部在網站上完成，改完立即生效。
GitHub → Actions重新部署、清空資料。
cron-job.org確認提醒信排程還活著、手動補跑一次。
GitHub → Code只有要退回舊版本時才會用到。

重新部署（例如程式有更新）

  1. Actions → 左側 Deploy → Run workflow → Run workflow。

退回上一個版本

  1. 點 Code 分頁 → 點檔案清單上方的 Commits。
  2. 找到造成問題的那一次變更，點進去。
  3. 右上角 ⋯ → Revert。
  4. 點 Create pull request，再點 Merge pull request。
  5. 回到 Actions → Deploy → Run workflow 重新部署。

退版只會還原程式，既有的預約、成員、會議室資料都會保留。

定期確認提醒信還在跑

登入系統 → 管理後台首頁 → 看「提醒信最後執行時間」。若停在很久以前，登入 cron-job.org → 點該工作 → 確認 Enabled 是開的 → 按 TEST RUN 立即補跑一次。記得同時檢查 Keep awake 那個工作。

緊急止血：讓系統暫停寄信

如果系統開始寄出不該寄的信，不需要重新部署：登入管理後台 → 系統設定 → 把 reminders_enabled 關閉並儲存，提醒信立刻停止。

常見問題

網站打開很慢，一直轉圈圈

免費方案在 15 分鐘沒人使用後會休眠，下一個人開啟時需要約 1 分鐘喚醒。喚醒後就恢復正常速度。這是正常現象，不是故障。

部署失敗，出現紅色叉叉

點開紅色的步驟看訊息。如果寫著缺少某個設定，回到步驟 4 補上，注意名稱大小寫要完全一樣，然後重新執行一次。

收不到系統寄出的信

先看垃圾郵件匣。接著到管理後台的寄信紀錄頁面，看那封信的狀態是「已寄出」還是「失敗」，失敗會顯示原因。也請確認步驟 2 的寄件人地址已完成 Brevo 確認。

今天的信寄不出去了

免費方案每天上限 300 封，系統設定的安全上限是 280 封。超過之後會優先停掉會議提醒信，但驗證信、邀請信、密碼重設信、預約被取消的通知信仍照常寄出。隔天自動恢復。

我想改預約規則

管理後台 → 系統設定，每一項旁邊都有中文說明。改完立即生效，不需要重新部署。

資料會不會不見

不會。Neon 免費方案不會刪除資料。系統也永遠不會真正刪除預約紀錄：取消或被覆蓋的預約會保留成歷史，方便日後查詢。

要怎麼退回上一個版本

在 GitHub 找到出問題之前的版本，用 Revert 產生一個還原版本，再到 Actions → Deploy → Run workflow 重新部署一次。詳細步驟見儲存庫裡的 ROLLBACK.md。
